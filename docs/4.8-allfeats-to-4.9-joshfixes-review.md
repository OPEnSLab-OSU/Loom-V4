The largest changes are checked time and wake handling, SD writes that survive failures, length-aware MQTT streaming, modem-specific LTE recovery, and a scheduled LoRa journal whose receipt means the hub saved the data. ### What happened to the 2 KB buffer?

**The 2,000-byte limit still exists.** Manager keeps one heap-backed ArduinoJson document with `MAX_JSON_SIZE` capacity and reuses it every cycle. ArduinoJson's capacity is memory for the document, while the networking limit is checked separately against serialized bytes. Several 2,000-byte *text copies* went away.

| Path | 4.8 allFeats | 4.9 Josh fixes |
| --- | --- | --- |
| Manager packet | One 2,000-byte JSON pool. Clearing it each cycle was already present. | Same pool, plus an overflow flag checked by persistence and publish paths. The compatibility `getJSONString()` still takes a caller-supplied buffer. |
| Debug display | Pretty JSON is serialized into a 2,000-byte stack array. | Pretty JSON streams to Serial and optional SD output. Formatted diagnostic messages still use a bounded 256-byte scratch buffer. |
| MQTT and MongoDB | A single publish serializes to a 2,000-byte char array. Batch upload fills another 2,000-byte array from SD. | Serialize directly to a length-declared MQTT packet or stream the SD body in 64-byte chunks. MQTT still rejects lengths at or above 2,000 bytes. |
| SD reads | `readFile()` reserves 5,000 bytes regardless of file size. | Allocates exactly file size plus a NUL, with a 4,999-byte ceiling. This per-file allocation is separate from JSON streaming. |
| Remote commands | Both the retained text and scratch JSON document use the 2,000-byte constant. | A 256-byte retained-message array and a small fixed JSON document handle known command fields. |
| LoRa | Fixed radio frame buffers with a larger temporary JSON document. | Frame buffers remain. Fragment reassembly allocates its 2,000-byte document lazily. An explicitly supplied receive pool reserves that RAM, and allocation failure rejects the fragment. Transmit-only nodes can leave the pool out. |

## 2. Hypnos, RTC, and SD

### 2.1 Verified time and alarm deadlines

**Data integrity and availability.** 4.8 used `RTC_DS.now()` directly to arm the alarm, then reconstructed or fetched the alarm time at sleep entry. A failed RTC transaction, stopped oscillator, or month rollover could produce an incorrect wake decision. 4.9 checks RTC status, verifies the write/readback, limits DS3231 date-mode alarms to a safe range, and compares the exact target that was armed. The legacy relative call is still available. Checked relative and absolute wake APIs let the sketch fall back when arming fails.

    // Datasheet sections 7.3/7.5: offset compensation must finish, CORDIC overflow invalidates
    // the conversion, and even parity protects all 18 serial bits. Zero is not a ready reading.
    if (data >= (1UL << 18) || (data & (1UL << OCF)) == 0 || (data & (1UL << COF)) != 0) {

    uint32_t parity = data;
    parity ^= parity >> 16;
    parity ^= parity >> 8;

    parity ^= parity >> 2;
    parity ^= parity >> 1;

### 7.3 Plan the radio rollout by protocol

Keep a hub and its nodes on a known-compatible protocol, schedule, and payload. The ordinary JSON/MessagePack path, the 4.8 LoRa rework, and the 4.9 scheduled SD journal have distinct delivery contracts. A compile-successful older node does not establish over-the-air compatibility.
